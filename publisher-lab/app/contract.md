# Studio App UI contract

**Current build: persistent WebKit execution adapter.** Requires `pluginContext.nativeCapabilities.sessionVersion === 1`, `sessionLoginOptionsVersion === 1`, `networkHeadersVersion === 1`, `persistentWebsiteSessionsVersion === 1` and `browserRequestsVersion === 1`. An older host is rejected with an update message before login or network calls. The plugin owns the platform login entry, add-versus-relogin flow, account verification and invalidation, business request headers, upload protocols, preparation and publication state. The host provides generic isolated persistent website containers, manifest permission enforcement, real page fetch execution, bounded body handles and durable noncredential plugin state. All platform API calls and uploads execute in the same account's WebKit website environment used for login; no URLSession or Chrome-extension fallback exists. The user has confirmed the workbench is usable; automated regression covers the execution contracts, while final publication status always follows the platform receipt.

`connect()` only checks session status and the real platform account. `importSession()` delegates to `platform/session.js`, calling `session.login{origin,url}` to add an account through the host's stable pending website container. `reloginSession()` calls `session.login{origin,url,profileId}` for the selected saved account, reusing its persistent website container. Neither call overrides the actual WebKit user agent. The host validates the authorized same-origin URL and presents a generic isolated website window; the plugin chooses the platform entry and verifies the actual account. Cookie values never enter plugin JavaScript.

Both login paths return an unverified candidate. Relogin checks the real account against the originally selected identity before `session.identify`; only successful verification commits to the original profile ID. A mismatch or failure clears only the candidate using `session.clear{origin,profileId,keepBrowserData:true}` and restores the original selection. This option is allowed only for an unidentified candidate: a new-account retry retains the stable pending website container; a relogin candidate retains the original shared container without making it a new-account pending slot. Adding an already saved identity returns `SESSION_ACCOUNT_EXISTS`, prompting the user to select that account and use “重新登录当前账号”; it does not replace that account's website container. `SESSION_LOGIN_CANCELLED` does not commit a new native API credential snapshot or change the selected account/drafts. A reused persistent website container may have received writes from the website itself; cancellation does not promise to roll back those writes.

`clearSession()` removes the current saved account without `keepBrowserData`, so an explicit user removal also clears that account's website data. The host reports the native API credential snapshot retention deadline as `expiresAt` (currently at most eight hours, additionally bounded by cookie expiry). This is neither the platform login lifetime nor the website-data lifetime. Reopening the same account for login can reuse its persistent site cookies, localStorage and IndexedDB; the plugin still verifies the real account and interprets platform responses. The host's `session.status` and profile catalog expose `browserSessionAvailable`; this indicates that the persistent website environment exists, not that the platform considers the user logged in. Actual browser execution requires the host environment, never the API snapshot’s `hasCookies` or `expiresAt`. Local editing and saved-information reads remain available when that environment is offline. Expiry of the native API snapshot therefore neither forces a browser relogin nor discards website data.

Native operations use `pluginUI.postMessage({op,...params})` and the envelope `{ok:true,data}` or `{ok:false,error:{code,message}}`. `browser.request` takes `{origin,contextURL,profileId,requestId,url,method,headers,credentials:'session'|'omit',responseType:'text',bodyText?|bodyHandle?}` and returns `{status,headers,body,consumedBodyHandle?}` with at most 4 MiB response text. `origin` is the declared session origin, `contextURL` is the plugin-chosen same-origin page, and `profileId` is the explicit active account or unverified login candidate. The client captures this profile once per dispatch and carries it through all account checks, resource queries and uploads, including cross-origin `credentials:'omit'` requests. The host rejects stale profiles and enforces manifest URL, method and business-header permissions. Upload bodies use `body.begin`, `body.append` (at most 256 KiB decoded), `body.finish`, `body.remove` with an 80 MiB body limit; `session.cancel` never implies remote publication was revoked. `state.get{keys?}` / `state.set{values}` persist noncredential preparation, upload metadata and publication records separately from UI state.

`platform/browser-request.js` chooses the public creator upload page and binds the dispatch profile. The generic bridge executes `window.fetch` in that page's `.page` world, using the account's persistent website data. WebKit owns UA, language, Cookie, Origin, Referer and `Sec-*` headers; the plugin neither synthesizes nor requests manifest permission for them. Existing business Accept, Content-Type and upload signature fields retain their values and remain subject to `permissions.network[].allowedHeaders`. Browser CORS, preflight and redirect rules apply: a rejected or unreadable response fails without an alternate network transport. Running in the page world allows installed page hooks to execute, but does not guarantee arbitrary platform signatures, account challenges or final publication success. `pluginContext.browserEnvironment` is not used to construct request headers. Local media reads and HTML audio do not use this platform request adapter.

The UI imports `studioClient` from `./studio-client.js`. No page from the creator website is embedded. All execution requests use `await studioClient.request(operation, params, {onProgress, signal}?)`. `studioClient.onStatus(listener)` returns an optional unsubscribe callback. `connect()` is explicitly user initiated.

## Session and capabilities

`connect()` or `studio.session` returns `{connected, account, capabilities}`. Account is `{id, name, avatarURL?}`. Missing account means signed-out/unverified, never a demo identity. Status listeners accept this same shape plus `{message?,state?}`. Account changes invalidate prepared publication.

Hosts advertising `nativeCapabilities.sessionProfilesVersion === 1` support saved accounts. Client status also includes `profiles: [{id,accountId,name,expiresAt,hasCookies,browserSessionAvailable}]` and `activeProfileId`. `listAccounts()` reads the local paginated catalog only; opening the workbench never verifies or logs into a platform automatically. `selectAccount(profileId)` switches the explicit native profile and restores its known identity without a remote identity request. Profiles without an available website environment remain selectable and visibly require a fresh login; native API snapshot expiry alone does not change this state. `importSession()` adds a separate login, then binds the verified platform identity through `session.identify{origin,profileId,accountId,name}`; explicit relogin updates the original profile only after the candidate passes identity verification. `clearSession()` removes only the current profile. Cancellation preserves the previous account; failed verification marks it offline without erasing previously stored information. Account changes cancel in-flight reads; only upload/preparation/publication operations block account changes. All credentials remain inside the host; profiles are not serialized into work drafts.

Capabilities: `{operations: string[], limits?: {imageCount,titleLength,descriptionLength,coverBytes}, options?: {visibility: [{value,label}], download: [{value,label}]}, declarations?: [{id,label,description?,required?}]}`. `operations` is the explicit usable allowlist. Unsupported capabilities stay visibly disabled. No implementation may claim support before its execution contract is verified.

## Queries

`hotspots.search({query,kind,draftId?})` returns `{items:[{name,heat?,thumbnailURL?}],nextCursor:null,message?}`. Nonempty queries use the official hotspot search endpoint. Empty image queries use only the current draft's complete uploaded-image snapshot for recommendations, otherwise return an input hint without a platform request; video queries use the official empty-URI default recommendation. Selection stores the word in `draft.hotspot` (default `""`), independently of the description and topic IDs. Publication emits a nonempty value as `item.common.hot_sentence` for both images and videos. Selection does not add an account lookup or a separate hotspot verification. Creating new hotspot words is not exposed without the platform permission contract.

`users.search` uses recent contacts for an empty query and user search for a nonempty query. Both return `thumbnailURL`, `handle` (platform `unique_id`, falling back to `short_id`) and `followerCount` (nonnegative integer or `null`) for display. The contact dropdown shows these fields without an additional account request; missing details remain absent, while a real zero follower count is displayed. Selected mentions still persist only `{id,name}`.

`topics.search`, `users.search`, `music.search`, `locations.search` take `{query,cursor?,kind}`; `collections.list` takes `{query?,cursor?,kind}`. Responses are `{items:[{id,name,description?,thumbnailURL?,previewURL?}],nextCursor?}`. Topic and user identities are saved separately from plain text. Explicitly selected name-only topics use `{id:"0",name}` following the official editor contract; multiple such topics are distinguished by name. A nonempty typed topic gets a local selectable suggestion when the current result has no exact match, including when remote search fails. AI copy begins with `#有序图库` on its own line, deduplicates that exact topic and appends the deterministic capture-date tag if available. It binds both topics this way when the user applies the copy; an existing same-name positive ID is retained. No topic lookup or account request is added for this binding. Plain unselected text remains text. The description mirror highlights both named topics and existing ID-bound topics without changing the input. Persistence retains these bindings. Publication emits numeric `hashtag_id:0` in `text_extra` and excludes zero from `challenges`. Music drafts retain only `{id,name}`. Verified platform query responses populate an in-memory candidate pool; explicit selection saves the real `previewURL` and `duration` in a separate bounded music record, isolated by host profile, platform account and music ID within this plugin/library scope. These records never contain Cookie values, session credentials or music-search authorization. Media details and response extensions are not copied into persisted drafts.

`music.select({id,keepIds})` saves an explicitly chosen song from the same profile/account’s verified in-memory candidates; it cannot accept a caller-supplied media URL or duration. `keepIds` includes the music IDs referenced by all current drafts plus the new ID (at most 41, for 40 drafts). The UI reuses pending saves and writes only unsaved draft changes before selection, so a failed draft write leaves the previous choice and its media record intact. Clean drafts are not written again. Selection removes only records in the same scope that are absent from `keepIds`. Browsing candidates are limited to 200 entries and 30 minutes in memory; selected records are separate, have no fixed TTL and are never evicted by candidate browsing. Persistent records are capped at 128 across scopes; a full store rejects another insertion instead of evicting an existing selection. Resolving an old choice may add its record without pruning other selections.

`music.resolve({id,refreshSource?:boolean})` resolves a previously selected song by its exact platform ID. It returns one normalized music item with `{id,name,description?,duration?,thumbnailURL?,previewURL?,userCount?}`; the caller cannot provide a name, arbitrary URL or alternate lookup strategy. The official music-info call verifies the original ID and current metadata on each resolution; a changed name with the same ID is still the selected song. Its observed response does not include a playback URL or duration. Playable data first comes from the same profile/account/music-ID selected record. If it is missing, a recent verified candidate may supply the source; otherwise recovery reads at most two recommendation pages and two favorites pages, matching the exact ID. After an audio failure, explicit `refreshSource:true` refreshes the source through that same bounded lookup. There is no saved-name search or substitution of a different ID. Failure preserves the saved choice and asks the user to select an available track again. Record persistence does not guarantee that a withdrawn song or an expired media URL remains playable. Video music remains unsupported.

`cover.frames` takes `{assetId}` and returns `{items:[{id,name,timeMs,thumbnailURL?}]}`. It remains hidden unless explicitly advertised. `cover.upload` takes `{assetId}` for a user-selected library image and returns `{id,name,thumbnailURL?}`. There is no whole-file base64 message or media persistence in frontend state; native body staging uses bounded transient chunks.

`locations.search` additionally requires explicit `cityCode` and `cityName` from bundled cities.json. Persisted location and the preparation snapshot retain these two fields only as lookup hints. Music supports keyword search, an empty query for the selected platform category, or a `https://v.douyin.com/...` music link; video music stays unavailable until its payload is verified.

## Draft and media

Media addition requires `pluginContext.nativeCapabilities.mediaSelectionVersion === 1`. After successful draft persistence, `assets.select{kind:'image'|'video',maximumCount,excludeAssetIDs}` opens the host's source grid. The host keeps this WebView mounted while hidden and resolves the native envelope with `{cancelled:boolean,assetIDs:string[]}` when the user confirms or cancels. The plugin verifies the initiating draft ID/type, fetches metadata for confirmed IDs and applies valid, distinct assets within remaining capacity. Cancellation makes no content change. Image removal only removes a body reference; the library file and any cover/crop referencing that image remain intact.

Image cover selection offers both the current draft's images and “从图库选择”. Current-image choices use the separate lower-right selection control and explicit confirmation; an empty body opens the library selector directly. The cover selector requests one library image and writes only `cover`, never `assets`. An image cover's `assetId` need not occur in the body list. Selecting another cover clears its previous crop; selecting the same image preserves it. Cropping currently uses the first body image's aspect ratio, so it requires a body image. Changing or clearing the cover invalidates preparation without reordering the body. Video image-cover selection is not exposed until its UI flow is connected. Missing media-selection capability is an update error, never a fallback to immediate-add search.

Draft `{id,name,kind:'image'|'video',assets:[{id,name,kind}],title,description,topics:[{id,name}],mentions:[{id,name}],hotspot:string,music:{id,name}|null,location:{id,name}|null,collection:{id,name}|null,cover:{type:'asset'|'frame'|'upload',assetId?,id?,name?,timeMs?,crop?}|null,settings:{visibility,download,publishTime:'now'|'scheduled',scheduledAt,declarations:[string]},updatedAt}`. Media is identified by local library asset IDs; no file paths, media bytes, session cookies or credentials are persisted. The UI fetches library metadata/thumbnails with `pluginContext.apiBaseURL`, as the existing App plugin does. File-only browser previews never become uploadable library IDs.

Each local draft has an explicit delete action in the draft list. Confirmation removes only the selected local draft, including drafts with pending publication receipts; it never cancels a submitted publication, deletes library media or removes durable publication deduplication records. Removing another draft preserves the active draft and prepared content. Removing the active draft selects a remaining draft, or creates an empty editing entry when none remain.

Multiple local drafts use `pluginContext.frontendState` and native `pluginUI.postMessage({op:'persist',value})`; file preview uses a distinct localStorage key. Serialized state is version 2, allowlisted, small JSON. Writes are serialized and the UI reports saved only after native acknowledgment. Maximum 40 drafts; extra creation is declined rather than deleting drafts. `settings.scheduledAt` is kept as local form text in persistence and converted to timezone-explicit ISO in the publication snapshot.

During preparation, the native plugin resolves cover metadata through the same fixed local-library API as body media. It requires a real image type (`mediaType` normalized to `kind`, including Live Photo still-image resolution) and a source revision. Uncropped covers already in the resolved body reuse that body's upload; independent images and cropped covers use separate cover upload records scoped by account, resolved asset ID, revision and crop. Source identity/type/revision are checked around file preparation/upload and again before saving the publication snapshot. Any mismatch fails preparation without a publishable snapshot. Only the confirmed upload URI enters `item.cover.upload_poster`; `item.common.images` retains exactly the body's order and count. Neither remote cover URLs nor local file paths are accepted as asset identities.

Image order is the draft's `assets` order. Internal drag-and-drop or Option + Left/Right changes this order and persists it immediately; preview focus and cover/crop follow asset IDs. Reordering invalidates the prepared publication snapshot. Drag cancellation, outside data, stale draft scope, self-drop and busy operations do not reorder. Save failure retains the edited order with a native alert and an independent save retry.

## Prepare and publish

`publication.prepare({draft,requestId})` uploads/prepares the current immutable content snapshot. Asset progress carries `{phase,message,assetId,assetID,assetName,role}`; `role` is `image`, `cover` or `video`, and the name comes from resolved library metadata. The UI updates one row per role and asset ID, preserving independent covers and distinguishing a body image reused as the cover. `uploaded` is emitted only after the upload receipt and checkpoint are saved; `reused` denotes an existing confirmed upload. Failed or cancelled work must not overwrite completed rows. `{completed,total,countRole}` counts body images or video only, never the entire preparation including the cover and final checks; an overall percentage is shown only on a global event explicitly marked `scope:"overall"`.

Preparation does not require a previous page's in-memory candidate record. Existing topics with positive IDs, users, locations and collections are rebuilt from the current account's real platform queries, matching the exact ID; a renamed item with the same ID uses current platform metadata. Explicit name-only topics (`id:"0"`) use their validated names directly without lookup. Existing-resource lookup recovery follows server pagination for at most five pages and rejects repeated positions. Selected music uses `music.resolve({id})` before upload and again after upload; the returned ID must match, while the name may change. Music preparation obtains a fresh ID-validated detail response at both boundaries. The publishable duration comes from the bounded, account-scoped record populated by a verified platform music query. Music-info verifies identity, not duration; preparation fails if no valid media record can be resolved. Location extra fields and collection order likewise come from verified responses, never the draft. Activities are checked against the current directory and exact topic IDs from detail responses. Failed lookup preserves the draft and names the affected resource (`CHOICE_UNAVAILABLE`, `CHOICE_LOOKUP_FAILED`, or `CHOICE_LOCATION_CITY_REQUIRED`); preparation failures also use the host's native alert.

Prepare returns `{preparationId,account:{id,name},canPublish,issues?:string[],summary?:{title,assetCount,kind,visibility,scheduledAt},expiresAt?}`. A preparation is invalidated on ANY draft change or account change. `canPublish` must be explicitly true. Missing/unknown response fields cannot mean success.

`publication.publish({preparationId,requestId,expectedAccountId,confirmed:true})` is called only from a second confirmation dialog displaying the verified account and exact prepared work. No automatic publish, retry, navigation or hidden submit occurs. Confirmation is reset after each attempt.

Publish returns `{publicationId?,status:'published'|'scheduled'|'processing'|'failed'|'unknown',message?,url?}`. Only `published` means published, `scheduled` means scheduled, `processing` means still processing. Network/unknown outcome is shown as unconfirmed; the same requestId is retained for status queries and no automatic resubmission occurs. `publication.status({publicationId?,requestId})` explicitly refreshes the outcome using the same response.

Errors are Error objects with readable `.message` and optional `.code`. `AbortError` stops preparation/query transports and subsequent upload steps; completed upload metadata remains durable. Once final publication starts, the plugin continues collecting and persisting the receipt. Uncertain publication stays `unknown` without retry; cancellation never proves remote publication was revoked.

## Account errors and local editing

Opening or switching an identified host profile restores its known account and static plugin capabilities without a remote account lookup. Ordinary reads call their business endpoint directly. A session error marks the account offline and reports the error without clearing its display identity, drafts, selected resources or completed AI text. Existing local information remains editable; cached audio can still be attempted. Explicit login/session checks remain user actions. Preparation checks the account once at entry; actual publication checks once immediately before the POST. A successful platform receipt is persisted directly, without a later identity query changing it to unknown.

Read requests are cancelled on account changes and cannot apply late results to another profile. Upload/preparation/publication still block account switching. Publication status has per-draft loading state, permits editing and draft switching, and writes the result only to its initiating draft if the receipt is still the same. Closing cancels pending status reads; it never cancels an already submitted publication.
